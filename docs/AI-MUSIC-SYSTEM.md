# R-Music 系统定义（全新 AI 音乐系统）

> 本文是 `README.md` 的展开版：**它记录"我们打造的是什么、每个决策为什么这么定、现在到哪一步"**。
> 任何一次会话读到这里的结论，都不需要重新推导；要改结论请改本文，不要只在聊天里说。

---

## 1. 系统是什么

**一套自研的 AI 音乐系统。** 三件事合为一体：

1. **自己写的前端**（`web/`）：Vue 3 + Vite + TS + Pinia + Tailwind，Apple Music 极简风，三档自适应；
2. **自己的音源引擎**（`go-adapter/`，Go）：11 个平台的搜索/解析/直链，跑在国内原生 IP 上；
3. **大模型做调度大脑**（`ai_service/server.py` + DeepSeek）：理解人话、编排检索、终审选源、记住口味。

旧形态（YesPlayMusic 预编译产物 + nginx 注入定制脚本）**已废弃**：注入方案的上限就是"改外观"，
而我们要的是"重新定义交互与音源"，那必须自己写。

## 2. 一次播放的完整状态机

```
用户点一首歌
   │
   ├─① 命中整曲缓存？ ──是──► 直接本地 Range 交付（毫秒级，可拖动）
   │
   ├─② 生成候选（按优先级）：
   │     自有 Go 音源引擎（多平台，严格匹配：歌名+版本+歌手，时长容差 8 秒）
   │        └ 规则匹配不到 → 大模型在"同曲不同写法"候选里终审（只接受同一录音）
   │     → 备用直链
   │
   ├─③ 逐个候选"整曲落盘"：下载 → 解析真实时长/容器 → 与元数据比对
   │     ├ 时长不符（30 秒试听、别版本）→ 拒绝，继续下一个候选
   │     └ 通过 → 落盘 + 回写来源与实测体积
   │
   ├─④ 全部候选失败 → 明确"无可用音源"（标记 + 定期复核自愈），绝不返回别的版本
   │
   └─⑤ 交付：/api/audio/proxy 支持 Range（HEAD 200 / GET 206），供浏览器、
        Music Assistant、DLNA 渲染器与 ffmpeg 取流
```

**只有第 ③ 步的字节是真相。** HTTP 200、URL 合法、接口返回非空，都不算成功。

## 3. 决策记录（ADR）

| # | 决策 | 理由 | 状态 |
|---|---|---|---|
| ADR-1 | **音源以自有 Go 服务为主力**，网易云不做音源 | 用户指令；网易云对未登录请求压制歌手库、VIP 曲只给 30 秒试听，是长期瓶颈；自有引擎跨 11 平台，可控可测 | **决策已定 / 落实中**（见 §6） |
| ADR-2 | 网易云只保留"目录"角色（歌单/专辑/歌手/歌词/封面/推荐） | 目录层它做得成熟，且与音源可否播放无关 | 现行 |
| ADR-3 | AI 直连 DeepSeek 官方，配模型自动降级 | 经网关时单模型 503 会让全部 AI 功能瘫痪；直连少一跳 | 现行 |
| ADR-4 | 音源适配器**原生部署在国内机**，东京只转发 | 国内平台签名/出口有地域要求；每请求挂代理又慢又易超时 | 现行 |
| ADR-5 | **整曲落盘后交付**，不做直通转发 | 一次解决三类问题：签名链接过期、上游抖动、拖动慢 | 现行 |
| ADR-6 | 前端**自研重写**，产物替换 `dist` | 注入方案改不了交互与布局；重写可回滚（nginx 与 `/api` 不动） | 已上线 |
| ADR-7 | 投屏**按打开页面的设备本地发现** | 云端在东京、设备在局域网，本来够不到；各浏览器用各自原生能力最可靠 | 已上线（AirPlay 实测出声） |
| ADR-8 | 缓存**双约束**（400 文件 / 2GB）+ 磁盘水位联动 | 单个 FLAC 可占几十 MB，只数文件数会撑爆磁盘 | 现行 |
| ADR-9 | 巡检**健康即静默**，同签名 2 小时去重 | 会叫的告警才会被看见；否则用户静音它，它就等于没有 | 现行 |

## 4. AI 能力的入选标准

只把"规则结构上做不到"的事交给大模型，且**每个 AI 结论都必须能被算术复核**：

| 能力 | 规则为什么不行 | 复核手段 |
|---|---|---|
| 意图分类（点歌/电台/续播/控制） | 自然语言没有稳定模式 | 控制类在前端执行，后端只回指令 |
| 检索词生成 | 一句话到检索条件没有映射表 | 生成后再走真实检索 + 探活，不合格就丢 |
| 电台策展 | 规则判不出"这首不属于深夜专注" | 只在**真实可播**列表里取舍排序 |
| 跨语言选源终审 | 判不了 `周杰伦 = Jay Chou` | 时长差 >35 秒、多出目标没有的版本标记 → 拒绝 |
| 口味记忆 | 无 | 只统计真实行为（听满 30 秒 / 3–20 秒切走） |

## 6. 音源主力迁移（ADR-1 落实）

**目标**：一次播放请求的候选优先级改为

```
自有 Go 音源引擎（多平台，按实测优先级）
      ↓ 全部失败
备用直链（可选保留，作为最后手段）
```

**不变量**：
- 匹配仍是"严格"语义（歌名+版本、歌手容忍写法、时长容差 8 秒），`loose` 只放宽标点写法；
- 仍保留大模型终审与时长/体积双校验；
- 取不到就明确报错，不占位、不伪造。

**首要动作**：用真实歌曲实测每个平台今天的可用性（能取到完整音源 vs 返回片段/报错），
据此排定优先级写进 `FALLBACK_SOURCES`；文档不承诺平台可用性，只承诺"测出来的结论"。

## 7. 路线图（候选，按价值排序）

1. **音源主力迁移落实**（ADR-1）→ 应显著提高完整播放率；
2. 目录层是否也自研聚合（换掉网易云 API）：成本高（封面/歌词/歌单结构都要自己归一化）；
3. PWA 可安装 + 离线曲库（缓存已落盘的整曲）；
4. AI 歌单管理：整理、去重、挑出无音源、按场景重排；
5. 移动端手势（上滑全屏播放器、左右滑切歌）。
